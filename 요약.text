[1. 사전 데이터 준비 / 인덱싱]

원본 문서 (TXT, PDF 등)
   ↓
텍스트 추출 및 정리
   ↓
Chunking (글자 단위 / 문장 단위)
   + Overlap (문맥 보존을 위해 일부 내용 중복)
   ↓
각 Chunk Embedding (embeddinggemma)
   ↓
DB 저장 (Chunk 원문 + 벡터 + ID 등 메타데이터)
   ※ 현재 학습: SQLite / 벡터는 JSON으로 저장


[2. 사용자 질문 처리 / 검색 + 생성]

사용자 질문
   ↓
질문 Embedding (문서와 동일한 임베딩 모델)
   ↓
질문 벡터 생성
   ↓
저장된 Chunk 벡터와 유사도 계산 (코사인 유사도)
   ↓
유사도 높은 순서로 정렬
   ↓
Threshold 필터링 (기준 점수 미만 제외)
   ↓
Top-K 선택 (상위 K개 Chunk만 사용)
   ↓
관련 Chunk가 있는가?
   │
   ├── NO → 근거 문서 없음 안내 / LLM 호출 없이 종료
   │
   └── YES
        ↓
     선택된 Chunk 원문 추출
        ↓
     사용자 질문 + Chunk 원문 + 지시문으로 프롬프트 구성
        ↓
     LLM (qwen3:1.7b)
        ↓
     최종 답변 반환

※ 현재 학습 구현은 SQLite에서 전체 Chunk를 읽어 애플리케이션에서 유사도 계산·정렬·Top-K 선택.
※ 실제 대규모 서비스는 pgvector 등 벡터 인덱스/검색 기능을 활용할 수 있음.
※ Threshold와 Top-K 적용 순서는 설계에 따라 달라질 수 있음.


[3. 검색 품질 평가 / 별도 실행]

평가용 질문 + 정답 Chunk(ground truth) 준비
   ↓
각 질문으로 실제 벡터 검색 실행
   ↓
유사도 순으로 정렬된 검색 결과 확보
   ↓
정답 Chunk의 순위 확인
   ├── Hit@K : 상위 K개 안에 정답이 있으면 1, 없으면 0
   └── RR    : 첫 정답 순위가 r이면 1/r, 없으면 0
   ↓
여러 질문의 점수 평균
   ├── 평균 Hit@K : 정답을 상위 K개 안에서 찾은 질문 비율
   └── MRR@K     : 첫 정답이 얼마나 앞에 나오는지 반영한 평균
   ↓
Chunking 방식, Overlap, K, Threshold 등을 바꿔 성능 비교

※ K는 검색 횟수나 질문 수가 아니라, 한 질문에서 확인하는 상위 검색 결과 개수.
※ Hit@K와 MRR@K는 높을수록 좋으며, 같은 질문 세트와 K로 비교해야 함.
※ 정답 문구 포함 여부(includes)는 학습용 간이 판정; 실제 평가는 정답 Chunk ID/관련성 라벨 권장.
※ 검색 평가 점수가 높아도 LLM 최종 답변의 정확도가 보장되는 것은 아님.


[4. 핵심 개념 한 줄 요약]

Chunking      : 긴 문서를 작은 단위로 나누기
Overlap       : Chunk 경계에서 문맥이 끊기지 않도록 내용 겹치기
Embedding     : 텍스트를 의미 비교용 숫자 벡터로 변환
Cosine 유사도  : 질문 벡터와 Chunk 벡터의 방향 유사성 측정
Threshold     : 관련성이 낮은 검색 결과를 제외하는 기준
Top-K         : 유사도가 높은 결과 중 최대 K개 선택
Ground Truth  : 평가에 사용할 미리 정한 정답 문서/Chunk
Hit@K         : 상위 K개 안에 정답이 존재하는가?
RR            : 첫 정답 순위의 역수 (1 / 순위)
MRR@K         : 여러 질문의 RR 평균 (상위 K개 기준)
RAG           : 관련 문서를 검색해 LLM 답변에 근거로 제공

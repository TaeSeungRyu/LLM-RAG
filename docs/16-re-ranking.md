# RAG 학습 노트 — Re-ranking(재정렬)

## 1. 한 문장 정의

**Re-ranking은 1차 검색으로 찾은 후보 Chunk를 질문과의 관련성에 따라 다시 점수화하고 순서를 바꾸는 과정**이다.

- **Embedding 검색**: 의미적으로 비슷한 Chunk를 빠르게 후보로 찾는다.
- **Re-ranking**: 후보 중 질문에 더 적합한 Chunk를 위로 올린다.
- **LLM**: 재정렬 결과에서 선택된 Chunk를 참고해 답변을 생성한다.

> Re-ranking은 **검색 성능을 개선하는 방법**이고, MRR·Hit@K·Precision@K 등은 **그 성능을 평가하는 지표**다.

## 2. 왜 필요한가?

질문: **“ABC 회사의 근무 시간은?”**

| 1차 검색 순위 | Chunk | 예시 유사도 |
|---|---|---:|
| 1 | ABC 회사는 주 5일 근무합니다. | 0.91 |
| 2 | ABC 회사의 근무 시간은 오전 9시부터 오후 6시까지입니다. | 0.85 |
| 3 | ABC 회사는 유연근무제를 검토하고 있습니다. | 0.80 |

질문에 직접 답하는 Chunk는 2위다. 재정렬 모델이 해당 Chunk를 더 관련 있다고 판단하면 1위로 올릴 수 있다. 위 수치는 **설명용 가상 값**이며, 재정렬이 항상 성공하는 것은 아니다.

## 3. 처리 흐름

```text
사용자 질문
   ↓
질문 Embedding 생성
   ↓
Vector DB에서 후보 검색 (예: 상위 10개)
   ↓
Re-ranker가 질문–Chunk 관련성 재평가
   ↓
재평가 점수로 정렬
   ↓
최종 Chunk 선택 (예: 상위 3개)
   ↓
LLM에 질문 + 선택된 Chunk 전달
   ↓
답변 생성
```

**1차 검색 후보 개수**와 **LLM에 전달할 최종 개수**는 다르게 설정할 수 있다.

## 4. Re-ranking 방법

| 방법 | 원리 | 장점 | 주의점 |
|---|---|---|---|
| 단순 키워드·규칙 기반 | 질문 단어와 Chunk의 일치도 등을 이용 | 구현·실험 쉬움 | 조사·동의어·문맥 이해 한계 |
| BM25 기반 | 단어 빈도와 문서 내 희소성 등을 활용 | 키워드 검색에 강함 | 의미적 관련성 판단에는 한계 |
| Cross-Encoder | 질문과 Chunk를 함께 모델에 입력하여 관련성 점수 산출 | 문맥을 반영한 정밀한 재평가 | 후보마다 추론 비용 발생 |
| LLM 기반 | LLM에 후보의 관련성을 판단하도록 요청 | 유연한 판단·설명 가능 | 느릴 수 있고 출력이 불안정할 수 있음 |

**주의:** BM25는 보통 1차 키워드 검색에도 많이 사용한다. 재정렬 단계에 쓰는 것도 가능하지만, BM25 자체가 전용 Re-ranker인 것은 아니다.

## 5. 학습용 keywords 예제

```typescript
const question = "ABC 회사의 근무 시간은?";

const keywords = question
  .replace(/[?.,!]/g, "")
  .split(/\s+/)
  .filter((word) => word.length >= 2);

console.log(keywords);
// ["ABC", "회사의", "근무", "시간은"]
```

- `replace`: 일부 문장부호 제거
- `split`: 공백으로 문자열 분리
- `filter`: 2글자 이상만 유지

Chunk에 해당 문자열이 포함되는지 세어 다음처럼 **학습용** 점수를 만들 수 있다.

```typescript
const matches = keywords.filter((word) =>
  content.includes(word)
).length;

const keywordScore =
  keywords.length === 0 ? 0 : matches / keywords.length;

const rerankScore =
  similarityScore * 0.7 + keywordScore * 0.3;
```

**중요:** `70% + 30%`는 이해를 위한 임의의 가중치다. 실제 정답률을 뜻하지 않는다. 유사도와 키워드 점수의 범위 및 분포도 다를 수 있으므로, 운영에서 그대로 적용하지 말고 평가 데이터로 검증해야 한다. 실제 Re-ranking은 `keywords` 배열 없이도 가능하다.

## 6. Re-ranking을 어떻게 평가하나?

정답 Chunk가 2위 → 1위로 이동한 경우:

- **RR**: `1/2 = 0.5` → `1/1 = 1.0`
- **MRR**: 여러 평가 질문의 RR을 평균내면 변화 확인 가능
- **Hit@3**: 같은 3개 Chunk를 순서만 바꾸면 변하지 않음
- **Precision@3, Recall@3, F1@3**: 같은 3개를 순서만 바꾸면 변하지 않음

단, **최종 상위 1개 또는 2개만 선택한다면** 재정렬로 포함되는 Chunk가 바뀌어 Hit·Precision·Recall·F1도 달라질 수 있다.

### 평가할 때 비교할 항목

1. 동일한 질문·정답지로 **재정렬 전/후**를 비교한다.
2. `MRR@K`, `Hit@K`, `Precision@K`, `Recall@K`, `F1@K`를 목적에 맞게 확인한다.
3. **검색 지연 시간**, 모델 메모리 사용량, 최종 답변 품질도 함께 확인한다.

## 7. 중요한 한계

- Re-ranking은 **1차 검색 후보에 없는 Chunk를 새로 찾아내지 못한다.** 먼저 충분한 후보를 확보해야 한다.
- 재정렬 모델이 잘못 판단하면 오히려 순위가 나빠질 수 있다.
- 후보가 많을수록 처리 시간과 비용이 증가할 수 있다.
- Re-ranking 점수는 일반적으로 **정답일 확률**이나 **최종 답변 정확도**와 동일하지 않다.
- 재정렬 후에도 LLM이 잘못 답할 수 있으므로 답변 자체의 검증은 별도로 필요하다.

## 8. 현재 학습 환경에서의 적용

- **언어**: TypeScript / Node.js
- **임베딩**: Ollama `embeddinggemma`
- **생성 모델**: Ollama `qwen3:1.7b`
- **문서 저장**: SQLite Vector DB 실습

추천 실습 순서:

1. 기존 Embedding 검색에서 후보 Chunk 5~10개를 가져온다.
2. 후보별 `id`, `content`, 기존 `score`를 출력한다.
3. `qwen3:1.7b`에 질문과 각 Chunk를 제공해 관련성 평가를 요청한다.
4. 결과를 점수순으로 정렬해 최종 3개를 선택한다.
5. 기존 검색과 재정렬 결과를 나란히 비교하고 RR·MRR 및 처리 시간을 확인한다.

작은 로컬 LLM의 관련성 평가는 일관되지 않을 수 있으므로, 실제 품질은 평가 질문과 정답지로 확인한다.

## 9. 암기 요약

| 용어 | 핵심 기억법 |
|---|---|
| Embedding 검색 | **후보를 찾는다** |
| Re-ranking | **후보의 순서를 다시 매긴다** |
| Cross-Encoder | **질문과 Chunk를 함께 읽고 관련성을 평가한다** |
| MRR | **정답이 얼마나 앞에 나오는지 평가한다** |
| Top-K | **몇 개를 검색하거나 최종 선택할지 정한다** |

> **면접용 한 문장:** Re-ranking은 초기 검색으로 확보한 문서 후보들을 질문과의 관련성에 따라 재평가하고 재정렬하여, LLM에 더 적합한 근거 문서를 제공하는 검색 품질 개선 기법입니다.

## 10. 복습 문제

**Q1.** Re-ranking은 Vector DB에 없는 문서를 찾아낼 수 있는가?

**Q2.** 정답 Chunk가 7위에서 2위로 올라왔다면 RR은 어떻게 변하는가?

**Q3.** 상위 3개 Chunk의 순서만 바뀌었을 때 Hit@3는 달라지는가?

**Q4.** Re-ranking을 하려면 반드시 `keywords` 배열이 필요한가?

### 정답

1. **아니요.** 1차 검색 후보에 포함된 Chunk만 재정렬한다.
2. **1/7 ≈ 0.1429 → 1/2 = 0.5**
3. **아니요.** 같은 집합이면 Hit@3는 동일하다.
4. **아니요.** Cross-Encoder나 LLM 기반 방식은 별도 키워드 추출 없이도 가능하다.

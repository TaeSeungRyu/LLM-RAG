# RAG 최종 답변 품질 평가 — 반복 학습 노트

> 학습 범위: RAG 25일 차 및 평가 결과를 활용한 재시도 설계

## 1. 한눈에 보는 전체 구조

```text
질문
  ↓
Embedding(embeddinggemma) → 문서 검색(SQLite + 코사인 유사도)
  ↓
Re-ranking(qwen3:1.7b) → 최종 참고자료(Context)
  ↓
LLM(qwen3:1.7b) → 답변 생성
  ↓
최종 답변 품질 평가(LLM-as-a-Judge 등)
  ├─ 통과: 답변 전달
  ├─ 문서가 부족함: 질문 수정/Top-K 조정/재검색
  ├─ 문서는 충분하지만 답변이 잘못됨: 답변 재생성
  └─ 반복 실패: 근거 부족 안내
```

**중요:** 실제 사용자 질문마다 정답(Ground Truth)이 준비되어 있는 것은 아니다. 따라서 정답 비교 평가는 주로 검증 데이터셋으로 수행하며, 운영 중에는 근거 충실도 검사나 별도 검증 방법을 활용할 수 있다.

## 2. 핵심 용어 8개

| 개념 | 뜻 | 기억할 질문 |
|---|---|---|
| **Correctness (정답 정확성)** | 답변이 검증된 정답과 얼마나 일치하는지 | 답이 맞는가? |
| **Faithfulness (근거 충실도)** | 답변 속 사실적 주장이 제공된 참고자료로 뒷받침되는지 | 문서에 근거가 있는가? |
| **Answer Relevance (질문 관련성)** | 답변이 사용자 질문에 직접적으로 응답하는지 | 질문에 답했는가? |
| **Ground Truth** | 사람이 검증했거나 신뢰할 수 있는 기준 정답 | 무엇이 정답인가? |
| **Context** | 검색 후 LLM에 전달한 문서·Chunk | 무엇을 참고했는가? |
| **Grounding** | 답변을 신뢰할 수 있는 근거에 연결하는 것 | 근거를 바탕으로 답했는가? |
| **Hallucination (환각)** | 근거가 없거나 사실과 다른 내용을 그럴듯하게 생성하는 현상 | 없는 내용을 만들어냈는가? |
| **LLM-as-a-Judge** | LLM에 평가 기준을 주고 답변을 채점·판정하게 하는 방법 | 모델이 답변을 어떻게 평가하는가? |

## 3. 실습 사례

- **질문:** ABC 회사의 근무 시간은?
- **참고자료:** ABC 회사는 오전 9시부터 오후 6시까지 근무합니다. 주 5일 근무제입니다.
- **검증된 정답:** 오전 9시부터 오후 6시까지입니다.
- **생성된 답변:** ABC 회사는 오전 9시부터 오후 6시까지 근무하며 재택근무도 가능합니다.

| 항목 | 판단 |
|---|---|
| Correctness | 근무 시간은 맞지만 추가된 재택근무 주장은 정답으로 확인되지 않음 |
| Faithfulness | 재택근무 가능 여부가 참고자료에 없으므로 근거가 부족함 |
| Answer Relevance | 근무 시간 질문에 답했지만 불필요한 내용이 추가됨 |

실제 `qwen3:1.7b` 실습에서 받은 결과:

```text
Correctness  = 0.75
Faithfulness = 0.00
Relevance    = 0.75
```

**주의:** 이 점수는 평가 모델의 판단이다. 0.75는 '75% 확률로 정답'이라는 뜻이 아니다. Faithfulness 0.00도 모든 문장이 틀렸다는 의미가 아니다.

## 4. 평가 지표의 구분

| 구분 | 대표 지표 | 평가 대상 |
|---|---|---|
| **검색 품질** | Hit@K, RR, MRR, Precision@K, Recall@K, F1@K | 검색된 Chunk의 관련성·순위 |
| **답변 품질** | Correctness, Faithfulness, Answer Relevance | 최종 생성된 문장 |

- **Hit@K:** 상위 K개에 정답 Chunk가 하나라도 있는가?
- **RR:** 첫 번째 정답 Chunk의 순위 역수(1/순위)
- **MRR:** 여러 질문의 RR 평균
- **Precision@K:** 상위 K개 중 관련 Chunk의 비율
- **Recall@K:** 전체 관련 Chunk 중 상위 K개에서 찾은 비율
- **F1@K:** Precision과 Recall의 조화평균

검색 지표가 좋아도 답변이 환각을 포함할 수 있다. 반대로 답변 평가 점수가 좋아도 검색 성능 전체가 좋다는 뜻은 아니다.

## 5. LLM-as-a-Judge 입력과 출력

평가 입력은 목적에 따라 달라진다.

```text
[질문] 사용자 질문
[참고자료] 검색 후 최종 선택된 Context
[정답] 검증된 기준 답변 (있을 때)
[생성된 답변] LLM의 실제 응답
[평가 기준] Correctness / Faithfulness / Relevance
```

학습용 출력 예시:

```json
{
  "correctness": 0.75,
  "faithfulness": 0.0,
  "relevance": 0.75,
  "reason": "근무 시간은 맞지만 재택근무 주장은 참고자료에 없음"
}
```

### 평가 시 주의사항

1. 점수 범위(예: 0~1)와 판정 기준을 명확하게 정의한다.
2. 동일한 모델이 생성과 평가를 모두 하면 편향이 생길 수 있다.
3. 평가 결과를 그대로 정답으로 간주하지 않는다. 사람 검토나 별도 검증을 병행한다.
4. 정답이 없는 실제 질문에는 Correctness를 정답과 직접 비교하기 어렵다.
5. 평가 기준, 모델 버전, 테스트 데이터셋을 고정해 비교해야 결과를 해석하기 쉽다.

## 6. Faithfulness를 주장 단위로 평가하는 방법

답변에 사실적 주장이 두 개 있을 때:

1. '근무 시간은 9~18시' → 근거 있음
2. '재택근무 가능' → 근거 없음

단순한 주장 단위 평가 예시:

```text
근거 있는 주장 수 / 전체 사실적 주장 수 = 1 / 2 = 0.5
```

이 계산은 **하나의 가능한 평가 방법**이다. 앞서 사용한 LLM 직접 점수(0.00)와 계산 방식이 다르며, 실제 서비스에서는 주장 분해 및 근거 판정 정확도도 검증해야 한다.

## 7. 점수가 낮을 때의 대응

| 문제 | 우선 고려할 조치 |
|---|---|
| 참고자료에 정답이 없음 | 질문 재작성, 검색 범위 확대, Top-K 조정, 재검색 |
| 참고자료는 맞는데 근거 없는 주장을 추가 | 기존 Context로 답변 재생성, 프롬프트 강화 |
| 관련 Chunk의 순위가 낮음 | Re-ranking 개선 |
| 질문에 직접 답하지 않음 | 질문 중심으로 답변 재생성 |
| 자료끼리 충돌함 | 출처·최신성 확인, 모호함 표시 |
| 반복 실패 | 추측하지 않고 답변 불가 또는 근거 부족 안내 |

**중요:** 낮은 점수가 나왔다고 매번 Embedding부터 다시 실행할 필요는 없다. 먼저 **검색 문제인지 생성 문제인지** 구분한다.

## 8. 자기 교정 RAG의 재시도 흐름

```text
검색 → Re-ranking → 답변 생성 → 품질 평가
                                  │
                      ┌───────────┴───────────┐
                    통과                    미통과
                      │                       │
                   답변 전달              원인 판단
                                             │
                                  ┌──────────┴──────────┐
                                검색 문제             생성 문제
                                  │                    │
                               재검색               재생성
                                  └──────────┬─────────┘
                                             ↓
                                         재평가
```

- **Corrective RAG (CRAG):** 검색 결과 품질을 판단하고 부족한 검색을 보완하는 접근
- **Self-RAG:** 검색 필요성과 생성 결과에 대한 자기 평가를 활용하는 접근
- **Adaptive RAG:** 질문의 성격에 맞춰 검색 전략을 달리하는 접근
- **Agentic RAG:** 에이전트가 검색·도구 사용·검증 등의 작업 흐름을 조정하는 접근

위 개념은 관련되지만 서로 동일한 알고리즘을 뜻하지 않는다.

### 재시도 시 반드시 정할 것

- 최대 재시도 횟수 (학습용 예: 2~3회)
- 시간 및 토큰 비용 한도
- 실패 원인에 따른 재검색/재생성 분기
- 반복 실패 시 중단하고 근거 부족 안내

재귀 함수가 필수는 아니다. `for` 또는 `while` 루프로도 구현할 수 있다.

## 10. 암기용 한 줄 정리

- **Correctness:** 답이 맞는가?
- **Faithfulness:** 문서에 근거가 있는가?
- **Relevance:** 질문에 제대로 답했는가?
- **Ground Truth:** 비교할 기준 정답
- **Context:** LLM에 전달한 참고자료
- **Grounding:** 근거 기반으로 답하도록 하는 것
- **Hallucination:** 근거 없거나 틀린 내용을 생성하는 것
- **LLM-as-a-Judge:** LLM이 답변 품질을 평가하는 것
- **검색 실패:** 다시 찾는다.
- **생성 실패:** 같은 근거로 다시 답한다.
- **반복 실패:** 무한 반복하지 않고 중단한다.

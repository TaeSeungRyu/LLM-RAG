# RAG 검색 평가 지표 핵심 정리

> 학습용 요약: Hit@K · RR · MRR · Precision@K · Recall@K

## 0. 먼저 기억할 것

이 다섯 가지는 **RAG의 검색 단계**에서 관련 문서를 잘 찾았는지 평가하는 지표다. **LLM이 생성한 최종 답변의 정확도를 직접 측정하는 것은 아니다.**

- **K(Top-K)**: 한 질문에서 상위 몇 개의 검색 결과를 평가할지 정한 개수. 질문 수가 아니다.
- **관련 Chunk(정답 Chunk)**: 해당 질문에 답하는 데 실제로 도움이 되는 문서 조각.
- **Ground Truth(정답지)**: 질문마다 어떤 Chunk가 관련 있는지 미리 판정한 기준. 일반적으로 테스트 데이터에 마련한다.
- **Similarity Score**: 검색 유사도 점수. 정답 여부나 정답 확률과 동일하지 않다.

## 1. 한눈에 보는 표

| 지표 | 핵심 질문 | 계산 | 범위 |
|---|---|---|---|
| **Hit@K** | 상위 K개 안에 관련 Chunk가 하나라도 있는가? | 있으면 1, 없으면 0 | 0 또는 1 (질문별) |
| **RR@K** | 첫 번째 관련 Chunk가 몇 위인가? | 첫 관련 Chunk 순위의 역수, 없으면 0 | 0~1 |
| **MRR@K** | 여러 질문의 RR 평균은? | 각 질문 RR@K의 평균 | 0~1 |
| **Precision@K** | 상위 K개 중 관련 Chunk의 비율은? | 상위 K개 중 관련 Chunk 수 / K | 0~1 |
| **Recall@K** | 전체 관련 Chunk 중 몇 개를 찾았는가? | 상위 K개 중 관련 Chunk 수 / 전체 관련 Chunk 수 | 0~1 |

※ 일반적인 Precision@K는 K개를 평가하는 정의를 사용한다. 실제 검색 결과가 K개보다 적을 때는 평가 규칙을 명시해야 한다. Recall@K는 전체 관련 Chunk가 0개인 질문의 처리 규칙을 별도로 정해야 한다.

## 2. 예제로 한 번에 이해하기

질문: **“A회사의 복지제도는?”**

정답지: 전체 DB에서 관련 Chunk는 **ID 1, 3, 5 (총 3개)**

K=3으로 검색한 결과:

| 순위 | Chunk ID | 관련 여부 |
|---|---|---|
| 1위 | 2 | ❌ |
| 2위 | 1 | ✅ |
| 3위 | 3 | ✅ |

- **Hit@3 = 1**: 3개 안에 관련 Chunk가 있다.
- **RR@3 = 1/2 = 0.5**: 첫 관련 Chunk가 2위다.
- **Precision@3 = 2/3 ≈ 0.6667**: 검색한 3개 중 2개가 관련 있다.
- **Recall@3 = 2/3 ≈ 0.6667**: 전체 관련 Chunk 3개 중 2개를 찾았다. (ID 5는 놓쳤다.)
- **MRR@3 = 0.5**: 평가 질문이 이 1개뿐이라면 MRR은 RR과 같다.

### MRR을 여러 질문으로 계산한다면?

| 질문 | 첫 관련 Chunk 순위 | RR@3 |
|---|---:|---:|
| 질문 A | 1위 | 1.0 |
| 질문 B | 2위 | 0.5 |
| 질문 C | 상위 3개에 없음 | 0 |

**MRR@3 = (1 + 0.5 + 0) / 3 = 0.5**

## 3. 헷갈리기 쉬운 차이

### Hit@K vs RR
- Hit@K: **찾았는가?** (1위든 3위든 하나라도 있으면 1)
- RR: **얼마나 앞에서 찾았는가?** (1위=1, 2위=0.5, 3위≈0.3333)

### RR vs MRR
- RR: **질문 하나**의 첫 정답 순위 점수
- MRR: **여러 질문**의 RR 평균
- 질문이 1개라면 **MRR = RR**

### Precision@K vs Recall@K
- Precision@K: **가져온 것 중** 관련 있는 비율 (불필요한 결과가 적은가?)
- Recall@K: **전체 관련 문서 중** 찾아낸 비율 (빠뜨린 결과가 적은가?)
- 예: 전체 정답 10개 중 K=5로 4개를 찾았다면 **Precision@5=4/5=0.8**, **Recall@5=4/10=0.4**

## 4. K를 늘리면?

- Hit@K, RR@K, Recall@K는 **검색 순위가 고정되고 관련성 판정도 같다면** K가 커질 때 감소하지 않는다.
- Precision@K는 K가 커지면서 **높아질 수도 낮아질 수도 있다**.
- K가 크면 관련 Chunk를 더 찾을 가능성이 있지만, 관련 없는 Chunk도 LLM에 더 많이 전달할 수 있다.
- **K를 높인다고 검색 순위 자체가 개선되는 것은 아니다.**

## 5. 실제 서비스에서 언제 쓰나?

| 상황 | 정답지 필요 여부 | 설명 |
|---|---|---|
| 일반 사용자 질문에 대한 실시간 검색 | 보통 없음 | Top-K, 유사도 점수, Threshold 등을 사용해 검색·답변 |
| 개발 중 검색 품질 검증 | 필요 | 질문과 관련 Chunk를 정해 지표 계산 |
| Chunking·Embedding 모델 변경 비교 | 필요 | 같은 평가 질문과 기준으로 전후 비교 |
| 운영 중 품질 점검 | 평가 대상에 필요 | 표본 질문에 사람의 판정 등을 붙여 오프라인/주기적으로 평가 |

**주의:** 정답지 없이 검색 결과의 유사도 점수만으로 Hit@K, MRR, Precision@K, Recall@K를 정확하게 계산할 수 없다.

## 6. 실무 평가에서 주의할 점

1. 한 질문에 **관련 Chunk가 여러 개**일 수 있다. 정답 문구 하나의 `includes()` 검사만으로는 놓칠 수 있다.
2. 가능하면 정답지에 **관련 Chunk ID 목록**을 기록하고, 사람이 검토한다.
3. **동일한 질문 세트, 동일한 정답 기준, 동일한 K**로 모델이나 Chunking 방식을 비교한다.
4. 검색 평가 지표가 좋아도 **최종 LLM 답변의 사실성·근거 충실도**는 별도 평가가 필요하다.
5. 여러 질문의 Hit@K 평균은 **평균 Hit@K(성공률)**, 여러 질문의 Precision@K 평균은 **Mean Precision@K**로 볼 수 있다.

## 7. 10초 암기 문장

> **Hit@K:** K개 안에 정답이 **있나?**
>
> **RR:** 첫 정답이 **몇 위인가?**
>
> **MRR:** 여러 질문 RR의 **평균은?**
>
> **Precision@K:** 가져온 K개 중 **몇 개가 관련 있나?**
>
> **Recall@K:** 전체 관련 Chunk 중 **몇 개를 찾았나?**
